Debugging Workflow

debuggingworkflow

Use a repeatable method to find bugs and fix them without stress.

Milestones

  1. Observe: Write what you expected vs what actually happened.
  2. Isolate: Test one script at a time by disabling others.
  3. Retest: Make one change, test again, and log the result.

Guide

Goal

Develop a calm, systematic way to debug Scratch projects. Debugging is not guessing. It is finding the smallest place where your prediction and the project disagree.

The debugging sentence

Before changing blocks, write or say:

I expected ___, but ___ happened.

Examples:

  • I expected the score to reset to 0, but it stayed at 6.
  • I expected the player to move right, but nothing happened.
  • I expected the win screen, but the backdrop stayed the same.

If you cannot finish the sentence, observe the bug again.

Try it

Add temporary say blocks to confirm which script is running.

when green flag clicked
say [Debug: script started] for (1) seconds

The 5-step debug loop

  1. Reproduce: Make the bug happen again.
  2. Isolate: Test one sprite and one script.
  3. Inspect: Check event blocks, selected sprite, variables, show/hide, and broadcasts.
  4. Change one thing: Make the smallest possible fix.
  5. Retest: Run the same test again.

Debug with visible clues

Use temporary messages to prove what is happening.

say (join [score: ] (score)) for (1) seconds

For touch bugs, use a color clue.

if <touching [Player v]?> then
  change color effect by (25)
end

Remove temporary clues when the real fix works.

Team debugging rule

The driver controls the mouse. The navigator reads the debugging sentence and checklist. Switch roles after one bug.

Checkpoint

You can explain the bug in one sentence, test one script at a time, and prove the fix worked.
